# 小米手环健康数据 MCP 工具 — 可行性调研

> 调研时间：2026-11-17
> 设备：MEIZU 21 / Android 16 / 无 Root
> 数据链路：小米手环 → Gadgetbridge（`nodomain.freeyourgadget.gadgetbridge`）→ Health Connect
> 目标：让 RikkaHub（`me.rerere.rikkahub`）里的 AI 读到步数、心率、睡眠

---

## 结论

**可以，但不要经过 Health Connect。**

推荐路线：**Gadgetbridge 自动导出 SQLite 文件 → 在 proot 里跑本地 HTTP MCP 服务 → RikkaHub 连 `http://127.0.0.1:<端口>/mcp`**。

理由：手环数据本来就是 Gadgetbridge 写进 Health Connect 的，直接读 Gadgetbridge 自己的库是同一份数据的上游，信息更全（分钟级心率、睡眠阶段），且不需要任何 Android 权限申请，不用 root，也不用写原生 App。

---

## 一、proot 里能否直接访问 Health Connect？

**不能。** 以下是在本机实测的结果，不是推断：

| 检查项 | 实测结果 | 说明 |
|---|---|---|
| `/dev/binder*` | 不存在 | proot 内无法进行 Android Binder IPC |
| `/system/bin/app_process64` | 启动失败：`library "libnativeloader.so" not found` | ART 运行时起不来 |
| linker 配置 | `failed to find generated linker configuration from "/linkerconfig/ld.config.txt"` | 缺少 Android 运行时环境 |
| `/system/bin/content` | 失败：`app_process: inaccessible or not found` | 它只是个包装 `app_process` 的 shell 脚本 |
| `/system/bin/am`、`cmd` | 不可用 | 同上，依赖 Android 运行时 |
| `/system/bin/getprop` | **可用** | 但 property service 与 App 权限无关，不能读数据 |

补充判断：

- 即使绕过运行时限制，proot 内进程的真实身份是 DSH App 的 UID，没有 `android.permission.health.READ_STEPS / READ_HEART_RATE / READ_SLEEP`，Health Connect 的 ContentProvider 也不对外导出。
- 换用手机侧的 Shizuku / ADB（`mcp__phone__android_shell`）也不行：它只能以 `shell`(UID 2000) 身份执行 `dumpsys healthconnect` 查看权限元数据、连接状态，**读不到健康记录本身**。

**结论：ContentProvider / Health Connect API 这条路在 proot 内走不通，属于环境层面的硬限制。**

## 二、可行方案对比

### 方案 a：Gadgetbridge 自动导出文件（推荐）

**可行性：高。**

Gadgetbridge 自带「自动导出」，会按固定间隔把数据库导出成一个**普通 SQLite 文件**（后缀 `.db`，MIME `application/x-sqlite3`），写入用户在 SAF 里选定的固定位置，同名覆盖。proot 可直接读取 `/sdcard/...` 下的文件，用 Python 标准库 `sqlite3` 即可，不需要任何格式转换。

- **权限**：无额外权限，只需做一次系统文件选择器授权。
- **手动步骤**：
  1. Gadgetbridge → 设置 → 数据管理 → 自动导出（Auto export）
  2. 选择导出位置，例如 `/sdcard/Download/health/gb.db`
  3. 设置导出间隔（1–6 小时，按需）
  4. 给 Gadgetbridge 开**自启动**和**后台运行**（Flyme 会限制 WorkManager 定时任务）
- **工作量**：MCP 服务端 1–2 小时（步数/心率/睡眠 4–6 个工具 + 联调）。
- **缺点**：读的是导出快照，数据新鲜度受导出间隔限制。

### 方案 b：Gadgetbridge 的 HTTP 接口 / Intent API

**可行性：部分可用，但不适合做数据源。**

- **没有本地 HTTP 接口。**
- 有 [Intent API](https://gadgetbridge.org/internals/automations/intents/)，需在设置里显式开启：
  - `nodomain.freeyourgadget.gadgetbridge.command.ACTIVITY_SYNC` —— 触发数据同步（可用 `dataTypesHex` 指定类型）
  - `nodomain.freeyourgadget.gadgetbridge.command.TRIGGER_EXPORT` —— 触发数据库导出
  - `...action.DATABASE_EXPORT_SUCCESS` / `DATABASE_EXPORT_FAIL` —— 导出结果广播
- **关键限制**：它只能触发动作，**不返回数据**；而 proot 发不出广播（无 Binder / 无 `am`），只能靠 Shizuku/ADB 逐条人工确认执行，无法自动化。
- **定位**：只能作为「手动刷新数据」的补充手段，不能当主数据通道。

### 方案 c：从 proot 用 adb / content query 读 Health Connect

**可行性：不可行。**

- proot 内没有可用的 `adb`，也没有 Binder；
- `content query` 依赖 `app_process`，已实测起不来；
- 即使通过 Shizuku/ADB 拿到 shell 身份，shell 也没有 `android.permission.health.*`，Health Connect provider 不导出；
- 唯一能做的是 `dumpsys healthconnect` 看**元数据**（已连接应用、权限、同步状态），读不到记录。

### 方案 d：写安卓原生插件 / 独立 App

**可行性：高，是最正规的方案。**

Kotlin 小 App：Health Connect SDK 读数据 + 前台服务 + 本地 Streamable HTTP MCP 端点。RikkaHub 直接连，常驻可用、数据实时。

- **权限**：在 Health Connect 中逐项授权 `READ_STEPS`、`READ_HEART_RATE`、`READ_SLEEP`；按规范还需要一个隐私说明 Activity（`ACTION_SHOW_PERMISSIONS_RATIONALE`），并在 Manifest 中声明对应 `uses-permission`。
- **手动步骤**：构建 APK（**最麻烦的一步**，手机上编不了，需要 PC + Android Studio，或用 GitHub Actions 云端构建），然后在 Health Connect 里逐项授权。
- **工作量**：1–2 天（开发 + 构建 + 授权流程 + 调试）。
- **定位**：方案 a 用起来不够实时、或需要跨 App 数据时再上。

### 方案 e：Health Connect 自带「导出数据」（兜底）

- 导出包是给「恢复」用的，内部格式没有公开文档，字段不透明，解析不可靠；
- 历史数据默认只有「授权前 30 天」窗口，更早的需要额外申请历史权限；
- 只能作为兜底，不建议做主线。

## 三、两个必须注意的前提

### 1. RikkaHub 的 MCP 传输方式

RikkaHub 只支持 **SSE** 和 **Streamable HTTP** 两种传输，**不支持 stdio**（见 [官方文档](https://docs.rikka-ai.com/zh/extensions/mcp)）。所以 MCP 必须是一个本地 HTTP 端点。

proot 与 Android App 共用同一个网络命名空间，`http://127.0.0.1:<端口>/mcp` 从 RikkaHub 可达。建议：

- 只绑定 `127.0.0.1`，不要 `0.0.0.0`；
- 用 RikkaHub 的 headers 功能加一个 `Authorization: Bearer <随机串>`，避免本机其他 App 扫端口读到健康数据。

### 2. 服务端存活

proot 里的进程是 DSH App 的子进程，App 被系统清理时会一起死。三种对策：

1. 给 DSH 关闭电池优化，保持后台运行；
2. 用 `nohup` / `setsid` 启动，并加一个 watchdog；
3. 把服务端放到 **Termux**（本机已安装 `com.termux`），用 `termux-wake-lock` + 开机启动脚本，稳定性更好。

## 四、建议的实施顺序

1. **先做方案 a 的最小版本**：Gadgetbridge 开启自动导出，选定路径与间隔；
2. 告诉我导出的文件路径，我先 `sqlite3` 核对表结构（步数 / 心率 / 睡眠对应的表名和字段，随 Gadgetbridge 版本略有差异）；
3. 写 MCP 服务端（Python + Streamable HTTP），工具建议：
   - `get_steps(days)` —— 每日步数汇总
   - `get_heart_rate(date, range)` —— 心率曲线 / 静息心率
   - `get_sleep(date)` —— 睡眠时段与阶段
   - `get_summary(date)` —— 当天概览（步数 + 心率 + 睡眠）
4. RikkaHub → 设置 → MCP → 添加 Streamable HTTP 服务器 → `http://127.0.0.1:<端口>/mcp` + Header；
5. 跑顺之后若觉得数据不够实时，再评估方案 d（原生 App）。

## 五、隐私提醒

健康数据属于敏感信息。无论哪条路线，都建议：

- 服务端只绑 `127.0.0.1`，加访问令牌；
- 导出文件放在固定目录，避免同步到网盘/云相册；
- 不要把导出的 `.db` 原文件贴到聊天、issue 或公开仓库里。
